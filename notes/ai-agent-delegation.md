# 从聊天到委托：AI Agent 协作入门笔记

> 本文基于明达（2026-07-14）的文章整理，面向零基础新手，帮你理解"怎样把 AI 从一个聊天工具变成真正的工作搭档"。

---

## 一、聊天 vs 委托：两种用 AI 的方式

### 什么是"聊天模式"？

你把数据丢给 AI，问一句"帮我看看有什么问题"，AI 很快给你一份分析。看起来很厉害，但：

- 它没排除退款数据
- 它不知道上周刚改过统计口径
- 它不会主动问你"给谁看的？什么标准？"

**你仍然在背后干所有活**：记进度、找问题、补信息、拼结果。AI 只是一个"快速回答器"。

### 什么是"委托模式"？

你把数据文件交给 Agent，**同时说清楚**：
- 分析目的（为什么要做）
- 业务背景（统计口径、特殊事件）
- 可用资料（哪些数据可以看）
- 交付形式（报告还是表格）
- 停止条件（什么情况必须停下来问你）

Agent 自行检查字段、处理异常、列出无法确认的问题，交回一份**附带计算依据的待审核报告**。你只需要判断结论是否成立。

### 核心区别

| 对比维度 | 聊天模式 | 委托模式 |
|---------|---------|---------|
| 谁推动任务 | 人（一步步推动） | Agent（自主推进，人到终点验收） |
| 连续性 | 人维持 | Agent 维持 |
| 人的角色 | 操作员 | 设计者/审核者 |
| 适合场景 | 简单问答、灵感激发 | 复杂分析、多步骤任务 |

> **一句话总结**：区分聊天和委托的关键不是提示词长短，而是——**在当前任务里，主要由谁维持连续性？**

## 二、怎样把任务说清楚

### 为什么"分析上周促销数据"不算一个好委托？

因为它藏了太多没说出口的前提：
- 给谁看？
- 时间范围？
- 销售额扣不扣退款？
- 异常怎么定义？
- 最终交什么？

**人做的时候靠经验和直觉补全这些空白，Agent 没有这些默认背景。没告诉它的信息，对它来说就不存在。**

### 一个能接手的委托，至少要说清五件事

1. **为什么做**（目的）
2. **依据什么**（数据和资料）
3. **不能越过哪些边界**（约束）
4. **最终交回什么**（交付物）
5. **什么时候必须停止**（停止条件）

### 清楚 ≠ 把整件事都交出去

- **可以交给 Agent 的**：能描述、能稳定执行、能客观检查的部分
- **必须保留人的判断的**：目标冲突、隐性约束、后果承担

> **新手提醒**：很多"AI 没理解我的意思"，不是提示词写得不够巧，而是你只说了"想做什么"，没说清"依据什么、做到什么程度、什么时候不应继续"。

## 三、人的角色转变：从操作员到设计师

### 聊天模式下，人最忙的事

上传资料 → 补充要求 → 提醒遗漏 → 搬运结果 → 发起下一轮

AI 加快了局部动作，但**工作的组织方式没变**。

### 委托模式下，人的工作移到两端

**开始之前**（设计）：
- 定目标：为什么存在这个任务？
- 给背景：哪些信息必须出现？
- 设规则：哪些步骤允许自主推进？
- 定标准：什么状态算"完成"？

**执行之后**（验收）：
- 证据是否支持结论？
- 结果是否达到标准？
- 能否进入真实工作？

> **一句话总结**：熟练执行者原本混在操作中的判断，现在要被**拆出来**，变成明确的目标、规则和完成标准。

## 四、习惯边界：为什么你总是忘记用 AI

### 一个常见现象

一个人写代码时 Agent 全程参与，可到了季度汇报，还是从空白文档开始手写。

他不是不知道 AI 能帮忙，只是"写总结"这个场景还没和 AI 建立联系——**任务一来，熟悉的动作自动启动**。

### 两种边界

- **能力边界**：AI 能做什么（不断扩展）
- **习惯边界**：你在什么时候会想起用 AI（往往不动）

> 工具能力不断扩展，习惯边界不动，新增能力也不会自动进入你的真实工作。

### AI-first 的正确理解

**不是**"什么都先扔给 AI"，而是——**在旧动作启动之前，多做一次分工判断**：

- 整项委托？（条件清楚、错误容易发现）
- 只委托一段？（Agent 整理初稿，人做取舍）
- 放在末端？（让 AI 检查遗漏、提出反面意见）
- 不用 AI？（这也是合理答案）

> **重点不在"用"，而在"先想过"。**

## 五、工作环境：AI 能否成为默认选择

### 一个扎心的事实

每次让 Agent 干活都要重新说明背景；资料要人工翻找再上传；关键决定只存在于聊天记录中——**Agent 执行只要几分钟，准备上下文却要半小时。**

### 好的工作环境长什么样

- 清楚的文件结构
- 可检索的资料
- 注明来源和日期的知识
- 能恢复当前状态的项目记录

**这些本来就是良好协作的基础，Agent 只是让它们多了一层作用**：不再只帮助人理解，还决定了 AI 能否独立接手工作。

> 如果每次用 AI 都要补同样的背景，问题可能不是 Agent 不够聪明，而是**你的工作环境从未准备好让新执行者进入**。

## 六、失败诊断：三层归因法

AI 出错时，**第一步不是重写提示词**，而是判断错误发生在哪一层。

### 第一层：能力问题

系统**无法稳定完成**任务中的核心判断。

- 擅长：提取、转换、归类、按规则计算（要求清楚、结果可验证）
- 不擅长：读出没写明的意图、预测不确定的变化、在冲突目标间取舍

> 注意：AI 的表达质量不会随可靠性同步下降。它在你熟悉和不熟悉的领域，都可能给出**结构完整、措辞笃定**的答案。看起来专业 ≠ 真的懂。

### 第二层：信息问题

完成任务所需的条件**没有进入上下文**。

例：Agent 汇总项目状态，把已取消的需求写成重点——因为你没告诉它上周评审的结果。

> 人自己没说清的问题，不会因为交给 AI 就自动变清楚。

### 第三层：机制问题

能力和资料都够用，但运行方式**没给错误留下暴露和纠正的机会**。

例：Agent 调接口没报错就宣布完成，但实际数据没更新。

### 归因错误的后果

| 真实原因 | 错误诊断 | 后果 |
|---------|---------|------|
| 能力不足 | "提示词不够好" | 不断加角色和警告，可靠性不变 |
| 信息缺失 | "模型不行" | 换模型，空白仍在 |
| 机制缺陷 | "偶发失误" | 只修了当前文档，下次原路出错 |

> **"AI 不靠谱"可以是一种警觉，却不能成为诊断。**

## 七、什么能力更耐久

### 领域理解不会随模型升级自动出现

同一份数据，懂业务的人看到的是：
- 某渠道刚换了流量入口
- 部分退款本周才入账
- 增长最快的品类调过统计口径

不懂的人只看到：销售额涨了、转化率降了。

> **模型升级改善推理和生成，却不会凭空补齐一个具体组织的历史。**

### 经验要被"写出来"才能跨工具迁移

一个人能看出文案"不对"，却说不清哪里不对——这种直觉对本人有用，对 Agent 几乎不可见。

**可迁移的经验**需要被写成可识别的差异：
- 哪些数据必须统一口径
- 哪类结论没依据就不能出现
- 什么情况需要停止并交还给人

> **真正耐久的**：理解领域、判断结果、外显经验，并根据新反馈持续修订它们的能力。

## 八、关键概念速查表

| 概念 | 通俗解释 |
|------|---------|
| **Context（上下文）** | 模型此刻能看到的全部信息，不只是你这句话，还包括历史、文件、工具返回结果 |
| **Harness（运行环境）** | 把模型、上下文、工具组织起来的那一层。同一个模型在不同环境里能力不同 |
| **Skill** | "这类任务通常怎么做"（跨任务复用） |
| **Spec** | "这一次要做成什么"（一次性） |
| **Workflow** | 任务内部怎么衔接（拉数据→分析→出图→等确认） |
| **Loop** | 同一目标是否再来一轮（测试没过就继续改） |
| **Queue** | 多项任务谁先处理 |

## 九、上下文工程：不是信息越多越好

### 常见误区

"背景不足？那就把整个知识库都丢给它！"

**问题**：资料之间会竞争注意力。三份文件（正式 PRD、旧评审纪要、昨天群聊），Agent 不知道以谁为准。

### 上下文需要秩序

- 哪些是已确认的事实，哪些只是待验证线索
- 哪个版本当前有效，旧版本为何被替代
- 冲突时以谁为准，无法判断时如何停止

### 最小充分原则

**作出当前判断不可缺少的信息，都应该同时可见；暂时不参与判断的资料，保持可发现即可。**

分阶段展开：
1. 开始阶段：目标、范围、时间区间
2. 比较阶段：各对象的详细信息
3. 结论阶段：只保留已确认事实和关键依据

### 长任务的信息管理

把任务信息分三层：
- **当前必须看到的**：本阶段目标、有效约束、刚确认的决定
- **按需读取的**：原始数据、详细规范、历史方案
- **追溯时使用的**：完整工具输出、被取代的版本、运行日志

> **上下文工程不是信息收集，而是信息取舍。价值不在体积，而在时机。**

## 十、任务拆解：从交付物反推

### 错误做法：从第一个动作开始

先找资料 → 再看数据 → 然后分析 → 最后写报告

这描述的是"准备怎样动手"，不是"最终交回什么"。

### 正确做法：从交付物反推

例：最终要一份月度经营分析，要求——
- 重要结论必须能回到数据
- 无法确认的解释要明确标记
- 计算口径必须可追溯

反推出中间阶段：确认范围 → 取得数据 → 处理异常 → 计算指标 → 识别变化 → 核对业务事件 → 形成结论 → 生成报告

### 每个步骤需要三个接口

| 接口 | 回答的问题 | 例子 |
|------|----------|------|
| **输入** | 这一步依据什么开始？ | 用哪份数据、什么口径、时间范围 |
| **输出** | 这一步具体交回什么？ | 指标表、计算口径、异常记录 |
| **验收** | 凭什么认为已完成？ | 数量核对、规则检查、复算 |

### 拆解的度

**不要拆得比错误更碎**。判断一个环节是否值得独立：
1. 结果会不会改变后续路径？
2. 失败后能否只重做这一段？
3. 是否存在独立的验收依据？

三个都否定 → 只是流程描述，不是必要接口。

> **步骤的重要性不由耗时决定，而由错误能向后传播多远决定。**

---

## 十一、三层验收：对不对、好不好、够不够

### 第一层：对不对（事实与真实状态）

- 竞品分析说某产品有三项功能 → 回到官方记录核对
- Agent 说某渠道收入增长 18% → 检查时间段、退款处理、统计口径
- 报告附了链接 → 不代表链接支持它的陈述（可能已过期，甚至虚构）

> **不要让产出成为自身的证明。**

### 第二层：好不好（是否完成了应有的判断）

事实正确只是底线。一份分析可以把所有数据写对，却只是按公司罗列，没说清差异为何重要。

质量需要明确：给谁用、被认可的同类材料有什么特征、哪些表达不符合组织语气。

### 第三层：够不够（是否遗漏了关键内容）

方案列了收益成本，却没讨论失败的退出方式；报告只呈现支持的证据，没处理反面材料。

**遗漏比错误更难发现**——错误数字可以核对，没进入结构的维度不会主动提醒你。

> **对了未必好，好了未必全。AI 产出最危险的时候，往往不是看起来粗糙，而是看起来过于完整。**

---

## 十二、验收强度跟着风险走

| 风险等级 | 场景 | 验收方式 |
|---------|------|---------|
| 低 | 内部头脑风暴、格式转换 | 轻检查 |
| 中 | 经营分析、项目计划 | 关键数字和核心假设需强依据 |
| 高 | 客户、资金、合同、正式发布 | 权威资料 + 人工确认 + 专业审核 |

**验收应优先放在**：
- 高影响的结果
- 难撤回的操作
- 会向后传播的环节（如数据口径，错了后面全错）

### 可信交付要保留什么

不只是结论，还要保留：
- 重要事实来自哪里
- 采用了什么口径
- 结论依赖哪些假设
- 哪些地方仍无法确认
- 过程中排除了什么

> 当有人追问"凭什么"时，答案要能回到真实材料，而不是让 AI 重新生成一套解释。

## 十三、授权与放手：四个变量

### "人在回路"不等于安全

- 人在场盯着屏幕 ≠ 清楚每次操作的后果
- "是否允许继续"的按钮 ≠ 一次有依据的判断
- Agent 在隔离环境处理数据副本，人暂时离开的风险可能很低

**HIL 与 AFK 描述的是人在哪里，不是 Agent 获得了多少权力。**

### 决定能放手多少的四个变量

| 变量 | 核心问题 | 例子 |
|------|---------|------|
| **可逆性** | 做错能不能撤回？ | 改文档副本可恢复；删数据库记录成本高 |
| **影响范围** | 错了会波及多少人？ | 个人草稿 vs 自动发给客户 |
| **可验证性** | 能不能独立确认真实结果？ | 代码可以跑测试；战略判断数月后才知对错 |
| **权限范围** | Agent 能碰到什么？ | 只读 vs 写入、测试环境 vs 生产环境 |

> 越可逆、影响越小、越易验证、权限越窄 → 自主空间越大。任何一项恶化 → 收紧授权。

---

## 十四、三类必须保留人工确认的动作

1. **不可逆或难撤回的**：正式发送、公开发布、删除数据、支付转账、签署合同
2. **高影响判断**：战略方向、预算分配、绩效结论、人员去留
3. **涉及信任的对外行为**："回复邮件"可能构成正式承诺，"更新客户信息"可能涉及隐私

> 不是因为 AI 不能参与，而是因为**后果仍由人和组织承担**。

### 能力组合本身也可能是风险

一个 Agent 同时能：读内部文档 + 处理外部内容 + 对外发邮件

三项单独看都合理，组合起来就可能形成数据泄露路径。**应该切断其中至少一环。**

---

## 十五、术语表

| 术语 | 通俗解释 |
|------|---------|
| HIL（Human-in-the-loop） | 人在回路：人在关键节点参与决策 |
| AFK（Away from keyboard） | 离场委派：人暂时离开，Agent 独立推进 |
| 上下文工程 | 组织 Agent 所需信息的艺术：什么该看到、什么该忽略、冲突时以谁为准 |
| 最小充分 | 信息不多不少，刚好够当前判断 |
| 三层归因 | 能力 / 信息 / 机制——出错后定位原因的方法 |
| 三层验收 | 对不对 / 好不好 / 够不够——判断产出能否放行的方法 |
| Skill | 跨任务复用的"怎么做"经验 |
| Spec | 一次性的"这次做什么"描述 |

## 核心金句摘录

1. > 区分聊天和委托的关键：**在当前任务里，主要由谁维持连续性？**

2. > 很多"AI 没理解我的意思"，不是缺一句更巧妙的表达，而是人只说了想做什么，没说清依据什么、做到什么程度。

3. > AI-first 的重点不在"用"，而在"先想过"。

4. > 如果每次用 AI 都要补同样的背景，问题可能不是 Agent 不够聪明，而是工作环境从未准备好。

5. > AI 产出最危险的时候，往往不是看起来粗糙，而是**看起来过于完整**。

6. > 放手不是更先进的姿态，它是一项关于权限、证据与后果的风险判断。
