## 一、核心主题一句话

> **做 AI 项目不只是"技术上能不能做"，而是"业务上该不该做、怎么量化价值、速度能不能赢过外面"。**

---

## 二、项目立项：指标定义的陷阱

### 携程的教训

> 十年前在携程，每个营销活动都必须量化对集团的贡献。
>
> 官方标准：每间夜消费 200 元 × 佣金率 10% = 利润 20 元。
>
> **问题**：所有活动都用同一套标准计算，导致：
> - 立项时数字很好看
> - 实际结果达不到预期
> - 老板追问时只能找借口（"暑期影响""其他因素"）

### 错在哪里？

```
❌ 统一标准 → 面向大学生和面向商旅人群用同一个转化率
❌ 只看收入 → 忽略了用户活跃度、讨论热度等软指标
❌ 结果倒推 → 活动没达标就找理由补救，而不是反思标准
```

## 三、多元化指标体系

### 建议的指标维度

| 维度 | 示例指标 |
|------|---------|
| **技术指标** | 响应时间、算法准确率、系统可用性 |
| **业务指标** | GMV、订单量、收入、转化率 |
| **运营指标** | 用户打开频次、讨论热度、分享率 |
| **客服指标** | 问题采纳率、转人工率、满意度 |

### 容易被忽略的指标

> 如果一项活动能让用户打开频次**从每月 1 次提升到每月 50 次**，这本身就是一个重要指标——即使它不直接带来收入。

> 💡 **核心原则**：不要把所有指标都简化为"收入"，要用开源的、多元化的维度来定义项目成功标准。

## 四、需求定制实战：燃气客服平台

### 项目背景

为燃气公司定制智能客服平台，涉及用户端（APP）和员工端（PC）。

### 需求梳理流程

```
Step 1：需求获取
├─ 用户访谈（用户端 + 员工端）
├─ 结合 AI 工具收集整理观点
└─ 梳理完整需求列表

Step 2：需求筛选
├─ P0/P1/P2 优先级排序
└─ 标注高价值需求点

Step 3：需求设计
├─ 功能组件图（不同视角）
└─ 用户旅程地图

Step 4：AI 化评估
└─ 哪些环节可以加入 AI？
```

### 用户需求的典型案例

| 需求 | 说明 | 实现难度 |
|------|------|---------|
| **多模态交互** | 拍燃气表照片 → AI 判断故障 | ⭐⭐⭐ |
| **智能工单** | 对话中自动生成维修工单 | ⭐⭐ |
| **情感分析** | 紧急场景（燃气泄漏）→ 直接联动 119 | ⭐⭐ |
| **跨系统整合** | 客服平台 + 工单平台打通 | ⭐⭐⭐ |
| **绩效考核** | 员工排班 + AI 培训（AI Coach） | ⭐⭐ |

> 💡 **设计原则**：只要有一个垂直领域产品，就试着将其抽象为更通用化的产品框架——这是一种思维习惯。

## 五、知识管理与 Workflow 搭建

### 行业标配能力

当前智能客服平台已经具备的标准化功能：

```
拖拽式 Workflow 搭建：
├─ 触发条件（用户说了什么/做了什么）
├─ 流程分支（不同场景 → 不同处理路径）
├─ 话术推荐（基于知识库的推荐回答）
├─ 引导流程（先问 A → 再看 B → 最后回复 C）
└─ 结果处理（解决/转人工/生成工单）
```

> 💡 **不仅客服**：运营团队也可以搭建对应的自动化流程——任何需要标准化处理的场景都适用。

## 六、技术评审：产品经理的参与方式

### 评审流程

```
产品需求评审会 → 技术评审会 → 立项评审会
```

### 产品经理在技术评审中的角色

| 关注点 | 具体问题 |
|--------|---------|
| **方案优化** | 这个方案是否足够优化？ |
| **数据安全** | 数据隔离做好了吗？敏感数据处理对吗？ |
| **成本评估** | 用什么 AI 工具/模型？成本多少？ |
| **测试验证** | 用已有评测数据集先跑一遍 |

> 产品经理在技术评审中扮演"吉祥物"角色——参与度不如技术团队深，但要**问对问题**。

## 七、AI 风控的现实困境

### AI 车险理赔的例子

```
人工理赔：赔付 2000 元
AI 理赔：  赔付 1500-1600 元（人工的 7-8 折）
```

**为什么 AI 赔得少？**

- 规避 AI 精度问题，尽量减少成本损失
- 涉及金钱和精细化风控的场景，目前仍依赖规则引擎

### 行业真实现状

> 蚂蚁集团在 AI 风控方面，对外宣传做了很多优化，但实际场景中 AI 仅作为参考，并未 100% 接管关键流程。
>
> **很多做 AI 的人会变得悲观**：见过太多"看起来好"的东西，实际操作中并没有想象的那么好。

> 💡 **建议**：对不确定是否该加 AI 的场景，先小范围测试。数据不好可以通过优化解决，但先别全盘否定。

## 八、项目生命周期管理与 TAPD

### TAPD 的 AI 能力

| 功能 | 说明 |
|------|------|
| AI 代码助手 | 读取 TAPD 需求值，辅助编写代码 |
| 自动关联需求单 | 代码完成后自动关联到对应需求 |
| 生成更新日志 | 需求完成时自动生成 changelog |
| 需求分析 | AI 辅助拆解和分析需求 |
| 资源调配 | 需求下发时自动匹配人员 |
| 代码质量检测 | AI 辅助 Code Review |

### 项目管理的 AI 化方向

```
需求分析 → 资源调配 → 风险管理 → 代码检测 → 关键指标仪表盘
   ✅          ⚠️          ✅          ✅          ✅
 已实现     初步实现     已实现      已实现      已实现
```

## 九、四个关键反思

### 反思 1：这个 AI 功能真的需要做吗？

> 很多时候大家做 AI 只是**为了做 AI**。
>
> 现在要真正思考：当前业务场景是否真的能通过 AI 增强？

### 反思 2：怎么证明 AI 的价值？

> GMV 增长了，是因为 AI 优化，还是因为暑假自然增长？
>
> **必须用 AB 测试来证明 AI 能力的独立价值。**

### 反思 3：拿来主义不丢脸

```
每周浏览 GitHub → 发现高质量开源项目 → 调整后直接使用
                                          ↓
                              快速试错 → 验证业务模式
                                          ↓
                              如果可行 → 再考虑是否内部重研
```

> 先验证业务模式，再回头做合规——这比一开始就投入大量成本研发更合理。

### 反思 4：你的速度比外面快吗？

```
大公司：立项 + 排期 = 半个月到一个月
小团队：可能已经做出了原型
```

> **思维转换**：假设 3 个月后一定有更好的开源方案出现——
>
> 那我**现在就开始搭建业务模式**，3 个月后直接用更好的技术能力。
>
> 这可能是你的反超机会。

## 十、商业画布：全局思考产品

### 九宫格商业画布

```
┌─────────┬─────────┬──────────┬─────────┬─────────┐
│ 关键伙伴 │ 关键活动 │ 价值主张  │ 客户关系 │ 渠道通路 │
│         │         │          │         │         │
│         ├─────────┤          ├─────────┤         │
│         │ 关键资源 │          │ 客户细分 │         │
│         │         │          │         │         │
│         ├─────────┴──────────┴─────────┤         │
│         │ 成本结构       │  收入来源     │         │
└─────────┴────────────────┴─────────────┴─────────┘
```

### 产品经理需要思考的维度

| 维度 | 核心问题 |
|------|---------|
| **问题** | 我要解决什么问题？ |
| **市场现状** | 当前市场针对该问题的解决方案是什么？ |
| **目标用户** | 我为哪些人提供解决方案？ |
| **产品卖点** | 即使同质化，我的差异化是什么？（价格/功能/文化） |
| **产品功能** | 实现卖点需要哪些核心功能？ |
| **推广渠道** | 通过什么渠道触达用户？ |
| **商业模式** | 收入来源和成本结构是什么？ |
| **数据指标** | 用什么维度评估项目成功？ |
| **竞争壁垒** | 我的模式为什么难以被复制？ |

### 蜜雪冰城的例子

> 价格便宜（5-6 元 vs 霸王茶姬 20 元），但有特定的目标用户群和产品文化。
>
> 卖点不仅是价格，还包括产品文化的完整性。

## 十一、六宫格简版：快速梳理思路

```
┌──────────────────────────────────────────────┐
│  1. 目标用户      谁？                         │
│  2. 应用场景      什么时候？什么情况下？         │
│  3. 要解决的问题   用户痛点是什么？              │
├──────────────────────────────────────────────┤
│  4. 产品方案      我打算怎么做？                 │
├──────────────────────────────────────────────┤
│  5. 成本考量      开发/人力/资源/时间成本         │
│  6. 预期收益      经济/时间/效率收益（尽量量化）   │
└──────────────────────────────────────────────┘
```

> 💡 **核心要求**：尽可能用**数据量化指标**来定义收益和成本。
>
> 因为最终做决策的老板，也需要一套评估标准来判断方案是否可行。

### 把自己当做 CEO

> 即使开发一个小产品功能，如果深入剖析，也可以拓展出更多维度。
>
> **把自己当做 CEO**：每个产品功能都应有一套完整的商业逻辑。

## 十四、学完之后想一想

1. **你现在的 AI 项目，能用什么指标证明 AI 的独立价值？** AB 测试做了吗？
2. **你的项目指标是不是太单一？** 除了收入，还有哪些维度值得追踪？
3. **你的开发速度比外面快吗？** 有没有可以"等 3 个月用开源方案"的技术投入？
4. **试着用六宫格梳理你正在做的产品功能**：用户、场景、问题、方案、成本、收益——每个都能量化吗？
5. **你浏览过 GitHub 上的开源项目吗？** 有没有可以直接"拿来"用的高质量项目？
