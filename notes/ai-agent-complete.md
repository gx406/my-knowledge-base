# AI Agent 完整学习笔记：从聊天到委托，从 Skill 到 Workflow

> 基于明达（2026-07-14）系列文章整理，面向零基础新手。
> 帮你理解：怎样把 AI 从聊天工具变成工作搭档，怎样把零散经验沉淀为可复用方法。

---

## 一、两种用 AI 的方式：聊天 vs 委托

### 聊天模式

你把数据丢给 AI，问一句"帮我看看有什么问题"，AI 很快给你一份分析。但：

- 它没排除退款数据
- 它不知道上周刚改过统计口径
- 它不会主动问你"给谁看的？什么标准？"

**你仍然在背后干所有活**：记进度、找问题、补信息、拼结果。

### 委托模式

你把数据交给 Agent，**同时说清楚**：分析目的、业务背景、可用资料、交付形式、停止条件。Agent 自行检查字段、处理异常、列出无法确认的问题，交回**附带计算依据的待审核报告**。

### 核心区别

| 对比维度 | 聊天模式 | 委托模式 |
|---------|---------|---------|
| 谁推动任务 | 人（一步步推动） | Agent（自主推进，人到终点验收） |
| 连续性 | 人维持 | Agent 维持 |
| 人的角色 | 操作员 | 设计者/审核者 |
| 适合场景 | 简单问答、灵感激发 | 复杂分析、多步骤任务 |

> **区分聊天和委托的关键不是提示词长短，而是——在当前任务里，主要由谁维持连续性？**

## 二、怎样把任务说清楚

### 为什么"分析上周促销数据"不算好委托？

它藏了太多没说出口的前提：给谁看？时间范围？扣不扣退款？异常怎么定义？最终交什么？

**人做的时候靠经验和直觉补全空白，Agent 没有这些默认背景。没告诉它的信息，对它来说就不存在。**

### 一个能接手的委托，至少说清五件事

1. **为什么做**（目的）
2. **依据什么**（数据和资料）
3. **不能越过哪些边界**（约束）
4. **最终交回什么**（交付物）
5. **什么时候必须停止**（停止条件）

### 清楚 ≠ 把整件事都交出去

- **可以交给 Agent**：能描述、能稳定执行、能客观检查的部分
- **保留人的判断**：目标冲突、隐性约束、后果承担

> 很多"AI 没理解我的意思"，不是提示词写得不够巧，而是你只说了"想做什么"，没说清"依据什么、做到什么程度、什么时候不应继续"。

## 三、人的角色转变：从操作员到设计师

### 聊天模式下，人最忙的事

上传资料 → 补充要求 → 提醒遗漏 → 搬运结果 → 发起下一轮。AI 加快了局部动作，**工作的组织方式没变**。

### 委托模式下，人的工作移到两端

**开始之前**（设计）：定目标、给背景、设规则、定标准。

**执行之后**（验收）：证据是否支持结论？结果是否达到标准？能否进入真实工作？

> 熟练执行者原本混在操作中的判断，现在要被**拆出来**，变成明确的目标、规则和完成标准。

## 四、习惯边界与 AI-first

### 一个常见现象

写代码时 Agent 全程参与，可到了季度汇报还是从空白文档开始手写。他不是不知道 AI 能帮忙，只是"写总结"这个场景还没和 AI 建立联系——**任务一来，熟悉的动作自动启动**。

### 两种边界

- **能力边界**：AI 能做什么（不断扩展）
- **习惯边界**：你在什么时候会想起用 AI（往往不动）

> 工具能力不断扩展，习惯边界不动，新增能力也不会自动进入你的真实工作。

### AI-first 的正确理解

**不是**"什么都先扔给 AI"，而是——**在旧动作启动之前，多做一次分工判断**：

- 整项委托？（条件清楚、错误容易发现）
- 只委托一段？（Agent 整理初稿，人做取舍）
- 放在末端？（让 AI 检查遗漏、提出反面意见）
- 不用 AI？（这也是合理答案）

> **重点不在"用"，而在"先想过"。**

## 五、工作环境：AI 能否成为默认选择

每次让 Agent 干活都要重新说明背景；资料要人工翻找再上传；关键决定只存在于聊天记录中——**Agent 执行只要几分钟，准备上下文却要半小时。**

好的工作环境需要：清楚的文件结构、可检索的资料、注明来源和日期的知识、能恢复当前状态的项目记录。

> 如果每次用 AI 都要补同样的背景，问题可能不是 Agent 不够聪明，而是**你的工作环境从未准备好让新执行者进入**。

## 六、上下文工程：不是信息越多越好

### 常见误区

"背景不足？那就把整个知识库都丢给它！"

**问题**：资料之间会竞争注意力。三份文件（正式 PRD、旧评审纪要、昨天群聊），Agent 不知道以谁为准。

### 上下文需要秩序

- 哪些是已确认的事实，哪些只是待验证线索
- 哪个版本当前有效，旧版本为何被替代
- 冲突时以谁为准，无法判断时如何停止

### 最小充分原则

**作出当前判断不可缺少的信息，都应该同时可见；暂时不参与判断的资料，保持可发现即可。**

分阶段展开：开始阶段（目标、范围）→ 比较阶段（详细信息）→ 结论阶段（已确认事实和关键依据）

### 长任务的信息管理

把任务信息分三层：
- **当前必须看到的**：本阶段目标、有效约束、刚确认的决定
- **按需读取的**：原始数据、详细规范、历史方案
- **追溯时使用的**：完整工具输出、被取代的版本、运行日志

> **上下文工程不是信息收集，而是信息取舍。价值不在体积，而在时机。**

## 七、任务拆解：从交付物反推

### 错误做法

先找资料 → 再看数据 → 然后分析 → 最后写报告。这描述的是"准备怎样动手"，不是"最终交回什么"。

### 正确做法：从交付物反推

例：最终要一份月度经营分析，要求结论可追溯、不确定处明确标记、口径可追溯。

反推出中间阶段：确认范围 → 取得数据 → 处理异常 → 计算指标 → 识别变化 → 核对业务事件 → 形成结论 → 生成报告。

### 每个步骤需要三个接口

| 接口 | 回答的问题 | 例子 |
|------|----------|------|
| **输入** | 这一步依据什么开始？ | 用哪份数据、什么口径、时间范围 |
| **输出** | 这一步具体交回什么？ | 指标表、计算口径、异常记录 |
| **验收** | 凭什么认为已完成？ | 数量核对、规则检查、复算 |

### 拆解的度

**不要拆得比错误更碎**。判断一个环节是否值得独立：
1. 结果会不会改变后续路径？
2. 失败后能否只重做这一段？
3. 是否存在独立的验收依据？

> **步骤的重要性不由耗时决定，而由错误能向后传播多远决定。**

## 八、三层验收：对不对、好不好、够不够

### 第一层：对不对（事实与真实状态）

- Agent 说某渠道收入增长 18% → 检查时间段、退款处理、统计口径
- 报告附了链接 → 不代表链接支持它的陈述（可能过期，甚至虚构）

> **不要让产出成为自身的证明。**

### 第二层：好不好（是否完成了应有的判断）

事实正确只是底线。一份分析可以把所有数据写对，却只是按公司罗列，没说清差异为何重要。

### 第三层：够不够（是否遗漏了关键内容）

方案列了收益成本，却没讨论失败的退出方式。**遗漏比错误更难发现**——没进入结构的维度不会主动提醒你。

> **AI 产出最危险的时候，往往不是看起来粗糙，而是看起来过于完整。**

### 验收强度跟着风险走

| 风险等级 | 场景 | 验收方式 |
|---------|------|---------|
| 低 | 内部头脑风暴、格式转换 | 轻检查 |
| 中 | 经营分析、项目计划 | 关键数字和核心假设需强依据 |
| 高 | 客户、资金、合同、正式发布 | 权威资料 + 人工确认 + 专业审核 |

### 可信交付要保留什么

不只是结论：重要事实来自哪里、采用了什么口径、依赖哪些假设、哪些地方无法确认、过程中排除了什么。

> 当有人追问"凭什么"时，答案要能回到真实材料，而不是让 AI 重新生成一套解释。

## 九、失败诊断：三层归因法

AI 出错时，**第一步不是重写提示词**，而是判断错误发生在哪一层。

| 层级 | 含义 | 例子 |
|------|------|------|
| **能力问题** | 系统无法稳定完成核心判断 | 擅长提取和计算，但不擅长读出没写明的意图 |
| **信息问题** | 所需条件没有进入上下文 | 把已取消的需求写成重点，因为你没告诉它评审结果 |
| **机制问题** | 运行方式没给错误留下暴露机会 | 调接口没报错就宣布完成，实际数据没更新 |

### 归因错误的后果

| 真实原因 | 错误诊断 | 后果 |
|---------|---------|------|
| 能力不足 | "提示词不够好" | 不断加角色和警告，可靠性不变 |
| 信息缺失 | "模型不行" | 换模型，空白仍在 |
| 机制缺陷 | "偶发失误" | 只修了当前文档，下次原路出错 |

> 注意：AI 的表达质量不会随可靠性同步下降。它在你熟悉和不熟悉的领域，都可能给出**结构完整、措辞笃定**的答案。看起来专业 ≠ 真的懂。

> **"AI 不靠谱"可以是一种警觉，却不能成为诊断。**

## 十、Skill：比提示词更值得保存的东西

### Skill ≠ 更长的提示词

| 对比 | 提示词模板 | Skill |
|------|----------|-------|
| 保存什么 | 减少重复输入 | 一类工作的处理方式 |
| 包含什么 | 措辞和格式 | 步骤、资料、标准、例外、停止边界 |
| 适合场景 | 边界清楚、一次交互完成 | 反复发生、有稳定方法、不能只靠机械规则 |

### Skill 保存的是"分寸"，不是"步骤"

- **只保存步骤**："先看标题 → 再看正文 → 最后给建议"
- **保存了分寸**：事实如何核对、哪些承诺没证据不能出现、何时必须停止改写

> 步骤容易复制，分寸才值得保存。

### 什么样的任务值得沉淀？

1. 这类任务是否**反复出现**？
2. 优秀结果与普通结果的差异**能否说清**？
3. 方法是否**相对稳定**？

三个都否定 → 过早封装只会把探索误写成规则。

### Skill 怎么写才好？

**好的起点不是空白模板，而是已经发生过的工作。** 真实任务让隐藏判断重新浮现：

- Agent 找出了语病，却没发现产品承诺缺乏依据 → 补充"核对产品文档"
- 下次开始核对事实，却引用了过期说明 → 补充"资料优先级和版本规则"
- 几次执行后，一套方法才逐渐显现

### 噪声比遗漏更致命

真实案例：某团队把技术评审经验写成 Skill，第一版 500+ 行 + 5 份补充文档。精简到 270 行 + 1 份模板后，评审得分反而**提高了近 9 分**。

> **让 Skill 变差的不是遗漏，是噪声——细节越多，核心判断越容易被掩埋。**

### Skill 的退化与治理

三种退化都源于同一动作——依据一次局部反馈修改长期方法：

| 退化类型 | 例子 |
|---------|------|
| **极端案例绑架** | 某文件解析失败，以后所有同类文件走更复杂路径 |
| **边界漂移** | 原本内容审核的 Skill 开始承担事实核验和项目归档 |
| **核心被埋** | 规则越来越多，核心标准反而被隐藏 |

治理方法：版本管理、回归验证、定期问"它现在是否仍然带来可验证的差异"。迭代不总是增加，也可能是删除、拆分，或交还给人。

## 十一、从 Skill 到 Workflow、Loop、Queue

### Workflow（工作流）

当你每次做竞品分析都按相似顺序调用几个 Skill，一条 Workflow 就自然出现了。

**关键判断**：下一步能否提前定义？
- 能提前定义 → 适合 Workflow
- 每步都要重新判断方向 → 更接近探索，强行编排会冻结不稳定的判断

**成本藏在步骤之间**：上一步输出 5 个字段，工具更新后变成 6 个；报告过去重视销售额，后来利润率才是主要目标。系统不报错，每一步都成功，却完成了已经不再需要的工作。

> 是否值得编排，不能只看能否自动化，还要看频率、路径稳定性和错误代价。

### Loop（循环）

Loop 适合能根据反馈逐步接近明确目标的任务。**前提不只是有反馈，而是系统知道什么叫结束。**

一条可靠的 Loop 至少能在这些情况下停下：目标达到、时间/次数/费用达到上限、连续多轮没有进展、高风险异常、无法自动判断的分岔。

三项额外前提：结果能被可靠判断、失败应能回退、成本要受控。

> Loop 的价值不在于永不停歇，而在于让能够客观改进的任务减少人工推动。

### Queue（队列）

当系统同时面对许多任务，问题变成"下一项该处理什么"。

**核心副作用**：10 个 Agent 可以并行生成 10 份结果，但如果最终都需要同一个人审核——任务只是在另一个位置排队。

> 自动化扩大了产能，却没有自动扩大**判断和责任的带宽**。

## 十二、方法的保质期：什么时候该退役

### 过期的方法不会报错

工具接口失效 → 系统明确报错。方法过期 → **没有明显故障**，只是人的修正越来越多。

三种过期信号：
1. 去掉某段复杂要求，结果几乎不变 → 方法不再制造真实差异
2. 维护成本超过收益
3. 方法稳定执行却服务于旧目标

> **最危险的自动化不是停止运行，而是稳定完成一项已经失去价值的工作。**

### 审视方法要回到最初

问三个问题：它当初解决什么问题？现在是否仍在解决？拿掉会发生什么？

维护动作不止"增加"：**简化**（核心仍有价值但结构可缩短）、**合并**（多个 Skill/Workflow 处理重叠问题）、**退役**（任务不再发生或系统已覆盖）、**升级**（业务变化需重新设计而非补丁）。

> **真正的浪费，不是让旧方法退出，而是为了证明过去投入有价值，继续为不再必要的系统支付维护成本。**

## 十三、执行变便宜后，价值去哪了

### 一项工作的三个部分

```
开始前（定义任务）→ 中间（执行）→ 交付前（判断结果）
```

Agent 首先压缩中间执行。**价值向两端移动**：
- **开始之前**：什么值得做？问题是否真实？目标是否正确？
- **交付之前**：什么可以接受？事实成立吗？遗漏足以改变判断吗？

> 执行越顺畅，**错误目标也越容易被高效实现**；产出越完整，**未经验证的结论也越容易被接受**。

### 判断力来自持续接触现实

判断力不是抽象天赋，而是在反复校准中形成：提出假设 → 看到结果 → 发现偏差 → 修正标准。

**自动化的悖论**：Agent 接过越多执行，人越容易远离形成判断所需的现场；而异常出现时，人又被要求迅速做出高质量决定。

**解法**：刻意保留与现实的连接——抽查原始证据、查看典型失败、理解规则为何变化、参与高价值例外、追踪重要决定的后果。

> 人可以退出重复操作，却不能同时退出学习回路。

### 责任不会随执行转移

组织不能因为 AI 做了执行就说"这是 AI 决定的"。责任至少意味着：
1. **知道结果依据什么**（关键事实、假设、不确定性）
2. **知道还有什么选择**（主要替代方案及为何没选）
3. **愿意承担并处理后果**（能解释、纠正、调整）

## 十四、授权与放手：四个变量

### "人在回路"不等于安全

人在场盯着屏幕 ≠ 清楚每次操作的后果。Agent 在隔离环境处理数据副本，人暂时离开的风险可能很低。

**HIL 与 AFK 描述的是人在哪里，不是 Agent 获得了多少权力。**

### 决定能放手多少的四个变量

| 变量 | 核心问题 | 例子 |
|------|---------|------|
| **可逆性** | 做错能不能撤回？ | 改文档副本可恢复；删数据库记录成本高 |
| **影响范围** | 错了会波及多少人？ | 个人草稿 vs 自动发给客户 |
| **可验证性** | 能不能独立确认真实结果？ | 代码可以跑测试；战略判断数月后才知对错 |
| **权限范围** | Agent 能碰到什么？ | 只读 vs 写入、测试环境 vs 生产环境 |

### 三类必须保留人工确认的动作

1. **不可逆或难撤回的**：正式发送、公开发布、删除数据、支付转账、签署合同
2. **高影响判断**：战略方向、预算分配、绩效结论、人员去留
3. **涉及信任的对外行为**："回复邮件"可能构成正式承诺，"更新客户信息"可能涉及隐私

> 不是因为 AI 不能参与，而是因为**后果仍由人和组织承担**。

### 能力组合本身也可能是风险

一个 Agent 同时能：读内部文档 + 处理外部内容 + 对外发邮件。三项单独看都合理，组合起来可能形成数据泄露路径。**应该切断其中至少一环。**

> 放手不是更先进的姿态，它是一项关于权限、证据与后果的风险判断。

## 十五、概念架构速查

### 四层关系

```
Prompt（你输入的）
  └── Context（模型能看到的全部信息）
        └── Harness（把模型、上下文、工具组织起来的运行环境）
              └── Agent（在以上支持下运行的形态）
```

### Harness 里的功能模块

| 模块 | 职责 | 通俗解释 |
|------|------|---------|
| **MCP** | 连接 | 标准协议，让 AI 接入外部数据和工具 |
| **Skill** | 方法 | "这类任务通常怎么做" |
| **Spec** | 定义 | "这一次要做成什么" |
| **Workflow** | 编排 | "多个步骤怎么衔接" |

MCP vs Skill：MCP 连上数据库 = 系统**有机会**取数据；Skill 知道查哪些表、用什么口径 = 系统**知道怎么**用数据。

### 从 Prompt 到 Loop 的演进（促销分析案例）

| 阶段 | 做法 | 人的角色 |
|------|------|---------|
| **Prompt** | "帮我分析上周促销数据" | 手动输入，得到通用回答 |
| **+ Context** | 粘入数据，说明对比维度 | 每周手动粘一遍 |
| **→ Skill** | 沉淀分析维度和格式 | 只给数据，按方法执行 |
| **→ Workflow** | 拉数据→分析→图表→结论→确认→发送 | 按一次按钮 |
| **→ Loop** | 每周一自动触发，异常标红 | 从"做分析"变成"审分析" |

### 错误诊断定位表

| 现象 | 问题多半在 |
|------|----------|
| 没指定时间范围和关注指标 | Prompt / Spec |
| AI 没看到退款数据和口径变化 | Context |
| 数据库连接失败却改用缓存 | 连接能力 / Harness |
| 分析方法只看销售额漏了毛利 | Skill |
| 先生成结论后检查数据 | Workflow |
| 工具失败后继续跑 | Harness 运行约束 |
| 文件生成就宣布完成 | Agent 完成状态判断 |

## 十六、日常工具箱速查

### 让输入更轻

| 技巧 | 适合场景 | 注意 |
|------|---------|------|
| **截图输入** | 界面报错、布局异常 | 遮挡敏感信息；截图只说明"看起来怎样"，真实状态还需回原系统 |
| **语音输入** | 快速捕捉想法、移动中 | 人名/术语/数字转写后复核；减少输入摩擦不等于让模糊意图变清楚 |
| **会议转录** | 提取决定和行动项 | 区分"讨论过""建议过""已决定"；行动项含负责人+交付物+时间 |

### 让资料可用

| 技巧 | 适合场景 | 注意 |
|------|---------|------|
| **项目空间/持久上下文** | 保存长期有效的项目背景 | 标记来源/版本/日期，定期清理失效内容 |
| **知识库问答** | 从组织资料中按需定位 | 说明来源是否权威、哪个版本有效、冲突时怎么处理 |
| **深度研究** | 多来源搜集、比较和综合 | 明确研究问题和排除项；抽查关键引用；不应自动成为决策依据 |

### 让长任务不断线

| 技巧 | 适合场景 | 注意 |
|------|---------|------|
| **会话交接** | 跨会话/跨人/跨 Agent 延续 | 保存目标、状态、已确认决定、约束、未完成事项 |
| **并行会话** | 独立的多项搜集/探索 | 确认无强依赖；多项并行不会自动扩大人的审查能力 |
| **AFK 离场委派** | 范围清楚的长任务 | 用副本/测试环境/脱敏数据；设停止条件；发布/删除/付费仍要人确认 |

### 让重复自动发生

| 技巧 | 适合场景 | 注意 |
|------|---------|------|
| **定时任务** | 日报、周报、巡检 | 定义数据截止时间、失败通知和停用条件 |
| **Hook 事件钩子** | 文件保存后跑测试、代码提交后检查 | 一个 Hook 一个职责；避免递归触发和静默失败 |
| **事件驱动工作流** | 新文件/工单出现后启动多步流程 | 设计去重、重试、回退、暂停和人工接管路径 |

### 跨过没有接口的地方

| 技巧 | 适合场景 | 注意 |
|------|---------|------|
| **界面操作** | 没有 API 的网页/桌面系统 | 测试账号+受限权限；点击成功 ≠ 目标完成 |
| **手机远程连接** | 查看长任务状态、处理异常 | 限制可见数据和可执行动作；不应成为绕过授权的通道 |

## 十七、术语表

| 术语 | 通俗解释 |
|------|---------|
| **Context（上下文）** | 模型此刻能看到的全部信息，不只是你这句话 |
| **Harness（运行环境）** | 把模型、上下文、工具组织起来的那一层 |
| **Agent** | 在以上条件支持下运行的形态，后续动作会根据前一步结果改变 |
| **MCP** | AI 连接外部数据和工具的标准协议 |
| **Skill** | 一类任务的"怎么做"操作手册，可跨任务复用 |
| **Spec** | 这一次具体做什么、做到什么程度 |
| **Workflow** | 多个步骤的编排顺序和异常处理 |
| **Loop** | 同一目标反复执行直到满足停止条件 |
| **Queue** | 多项任务的排序和调度 |
| **HIL（Human-in-the-loop）** | 人在回路：人在关键节点参与决策 |
| **AFK（Away from keyboard）** | 离场委派：人暂时离开，Agent 独立推进 |
| **Handoff** | 会话交接，让任务跨会话/跨人延续 |
| **Hook** | 事件钩子，在特定事件发生后自动触发动作 |
| **上下文工程** | 组织 Agent 所需信息的艺术：什么该看到、冲突时以谁为准 |
| **最小充分** | 信息不多不少，刚好够当前判断 |
| **三层归因** | 能力 / 信息 / 机制——出错后定位原因的方法 |
| **三层验收** | 对不对 / 好不好 / 够不够——判断产出能否放行的方法 |

## 核心金句摘录

1. > 区分聊天和委托的关键：**在当前任务里，主要由谁维持连续性？**

2. > AI-first 的重点不在"用"，而在"先想过"。

3. > 让 Skill 变差的不是遗漏，是噪声。

4. > AI 产出最危险的时候，往往不是看起来粗糙，而是**看起来过于完整**。

5. > 最危险的自动化不是停止运行，而是稳定完成一项已经失去价值的工作。

6. > 自动化不会把不可靠的方法变可靠，它只会放大。

7. > 人可以退出重复操作，却不能同时退出学习回路。

8. > 放手不是更先进的姿态，它是一项关于权限、证据与后果的风险判断。

9. > 真正的浪费，不是让旧方法退出，而是为了证明过去投入有价值，继续为不再必要的系统支付维护成本。

10. > 人的价值不在于还有多少工作必须亲手完成，而在于能否提出值得解决的问题、识别关键信息、处理例外，并为最终选择负责。
