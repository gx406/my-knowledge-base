# AI Agent 进阶笔记：Skill、Workflow 与实战工具箱

> 本文基于明达（2026-07-14）的文章整理，是《从聊天到委托》的续篇。面向有一定 AI 使用经验的新手，帮你理解"怎样把零散的 AI 使用经验沉淀为可复用的方法"。

---

## 一、Skill：比提示词更值得保存的东西

### Skill ≠ 更长的提示词

很多人第一次接触 Skill，觉得它就是一个"更详细的提示词模板"。**这是误解。**

| 对比 | 提示词模板 | Skill |
|------|----------|-------|
| 保存什么 | 减少重复输入 | 一类工作的处理方式 |
| 包含什么 | 措辞和格式 | 步骤、资料、标准、例外、停止边界 |
| 适合场景 | 边界清楚、一次交互完成 | 反复发生、有稳定方法、不能只靠机械规则 |

### Skill 保存的是"分寸"，不是"步骤"

例：让 Agent 审核营销文案——

- **只保存步骤的 Skill**："先看标题 → 再看正文 → 最后给建议"
- **保存了分寸的 Skill**：事实如何核对、哪些承诺没证据不能出现、何时必须停止改写、哪些只能标记交还给人

> 步骤容易复制，分寸才值得保存。

### 什么样的任务值得沉淀为 Skill？

问自己三个问题：
1. 这类任务是否**反复出现**？
2. 优秀结果与普通结果的差异**能否说清**？
3. 方法是否**相对稳定**？

三个都否定 → 过早封装只会把探索误写成规则。

### Skill 怎么写才好？

**好的起点不是空白模板，而是已经发生过的工作。**

真实任务会让隐藏判断重新浮现：
- 文案审核中，Agent 找出了语病，却没发现产品承诺缺乏依据 → 补充"核对产品文档"
- 下一次它开始核对事实，却引用了过期说明 → 补充"资料优先级和版本规则"
- 几次执行后，一套方法才逐渐显现

> 一次被接受和一次被否定的产出，可能都结构完整、语言流畅，**差别藏在信息取舍、证据使用和表达分寸里**。

### 噪声比遗漏更致命

一个真实案例：某团队把技术评审经验写成 Skill，第一版堆到 500+ 行 + 5 份补充文档。精简到 270 行 + 1 份模板后，评审得分反而**提高了近 9 分**。

> **让 Skill 变差的不是遗漏，是噪声——细节越多，核心判断越容易被掩埋。**

## 二、Skill 的退化与治理

### 三种常见退化

| 退化类型 | 表现 | 例子 |
|---------|------|------|
| **极端案例绑架** | 为一次特殊情况加永久规则 | 某文件解析失败，以后所有同类文件走更复杂路径 |
| **边界漂移** | 每次加一点，职责越扩越大 | 原本负责内容审核的 Skill 开始承担事实核验和项目归档 |
| **核心被埋** | 规则越来越多，核心标准反而被隐藏 | 报告变长、边缘情况覆盖更多，人反而要做更多修正 |

三种退化源于同一个动作：**依据一次局部反馈修改长期方法。**

### 怎样治理？

- **版本管理**：修改前要知道旧版解决什么
- **回归验证**：修改后用过去的典型任务重新比较
- **定期问**：它现在是否仍然带来**可验证的差异**？

> 迭代不总是增加，也可能是**删除、拆分**，或把尚不稳定的判断**交还给人**。

## 三、从 Skill 到 Workflow

### Workflow 怎样自然出现？

当你发现每次做竞品分析都按相似顺序调用几个 Skill：收集资料 → 核验来源 → 比较差异 → 生成报告——一条 Workflow 就自然出现了。

### 能串起来 ≠ 适合自动运行

**关键判断**：下一步能否提前定义？

- **能提前定义**（资料收集后总要核验来源，核验后进入比较）→ 适合 Workflow
- **每步都要重新判断方向** → 更接近探索，强行编排会冻结不稳定的判断

### Workflow 的成本藏在步骤之间

最常见的故障：**接口断裂**
- 上一步输出 5 个字段，工具更新后变成 6 个
- 文件路径改变，前面成功后面找不到产物

更危险的故障：**业务规则过期**
- 报告过去重视销售额，后来利润率才是主要目标
- 系统不报错，每一步都成功，却完成了已经不再需要的工作

> **是否值得编排，不能只看能否自动化，还要看频率、路径稳定性和错误代价。**

## 四、Loop（循环）：系统必须知道什么叫"结束"

### Loop 成立的前提

**不只是有反馈，而是系统知道什么叫结束。**

"继续优化，直到更好"**不是**停止条件——更好到什么程度？连续几轮没改善怎么办？成本是否超过收益？

### 一条可靠的 Loop 至少要能在这些情况下停下

- 目标达到
- 时间/次数/费用达到上限
- 连续多轮没有实质进展
- 出现高风险异常
- 遇到系统无法自动判断的分岔（如业务取舍、资料冲突）

### Loop 的三项额外前提

1. **结果能被可靠判断**（测试通过？数据满足规则？vs 文案是否更"打动人"？）
2. **失败应能回退**（在隔离环境修改副本，不是在生产系统反复调整）
3. **成本要受控**（每轮可能调用付费服务、消耗资源、让上下文膨胀）

> Loop 的价值不在于永不停歇，而在于让**能够客观改进的任务**减少人工推动。

## 五、Queue（队列）：瓶颈从执行转向审查

当系统同时面对许多任务，问题变成"下一项该处理什么"。

### Queue 的核心副作用

10 个 Agent 可以并行生成 10 份结果，但如果最终都需要**同一个人审核**——任务只是在另一个位置排队。

> 自动化扩大了产能，却没有自动扩大**判断和责任的带宽**。

---

## 六、方法的保质期：什么时候该退役

### 过期的方法不会报错

工具接口失效 → 系统明确报错。
方法过期 → **没有明显故障**，只是人的修正越来越多，结果与业务逐渐偏离。

### 三种过期信号

1. 去掉某段复杂要求，结果几乎不变 → **方法不再制造真实差异**
2. 维护成本超过收益
3. 方法稳定执行却服务于旧目标 → 优化的指标和资料没报错，只是业务已经关心别的事

> **最危险的自动化不是停止运行，而是稳定完成一项已经失去价值的工作。**

### 审视方法要回到最初

问三个问题：
1. 它当初解决什么问题？
2. 现在是否仍在解决这个问题？
3. 如果拿掉会发生什么？

### 维护动作不止"增加"一种

| 动作 | 场景 |
|------|------|
| **简化** | 核心判断仍有价值，旧结构可缩短 |
| **合并** | 几个 Skill/Workflow 处理高度重叠的问题 |
| **退役** | 任务不再发生，或系统默认能力已覆盖 |
| **升级** | 业务目标或风险条件变化，需重新设计而非补丁 |

> **真正的浪费，不是让旧方法退出，而是为了证明过去投入有价值，继续为不再必要的系统支付维护成本。**

## 七、执行变便宜后，价值去哪了

### 一项工作的三个部分

```
开始前（定义任务）→ 中间（执行）→ 交付前（判断结果）
```

Agent 首先压缩的是**中间执行**：搜索、整理、转换、计算、生成。

**价值向两端移动**：
- **开始之前**：什么值得做？问题是否真实？目标是否正确？
- **交付之前**：什么可以接受？事实成立吗？遗漏足以改变判断吗？

> 执行越顺畅，**错误目标也越容易被高效实现**；产出越完整，**未经验证的结论也越容易被接受**。

### 任务定义：为什么"分析客户流失"不算清楚

它至少包含几种不同问题：
- 找近期流失上升的直接因素？
- 判断哪些因素可以被业务改变？
- 支撑下一轮产品投入的决定？

Agent 都能回答，甚至更全面。但如果没有说清目的，**整套工作可能准确地回答了一个不重要的问题**。

### 判断力来自持续接触现实

判断力不是抽象天赋，而是在反复校准中形成的：
- 提出假设 → 看到结果 → 发现偏差 → 修正标准

**自动化的悖论**：Agent 接过越多执行，人越容易远离形成判断所需的现场；而异常出现时，人又被要求迅速做出高质量决定。

**解法**：不是让人重新做所有工作，而是**刻意保留与现实的连接**：
- 抽查原始证据
- 查看典型失败
- 理解规则为何变化
- 参与高价值例外
- 追踪重要决定的后果

> 人可以退出重复操作，却不能同时退出学习回路。

### 责任不会随执行转移

组织不能因为 AI 做了执行就说"这是 AI 决定的"。

责任至少意味着：
1. **知道结果依据什么**（关键事实、假设、不确定性）
2. **知道还有什么选择**（主要替代方案及为何没选）
3. **愿意承担并处理后果**（能解释、纠正、调整）

## 八、概念架构速查

### 四层关系：从一次交互到完整系统

```
Prompt（你输入的）
  └── Context（模型能看到的全部信息）
        └── Harness（把模型、上下文、工具组织起来的运行环境）
              └── Agent（在以上支持下运行的形态）
```

### Harness 里的功能模块

| 模块 | 职责 | 通俗解释 |
|------|------|---------|
| **MCP** | 连接 | 标准协议，让 AI 能接入外部数据和工具 |
| **Skill** | 方法 | "这类任务通常怎么做" |
| **Spec** | 定义 | "这一次要做成什么" |
| **Workflow** | 编排 | "多个步骤怎么衔接" |

### MCP vs Skill 的区别

- **MCP**：连上销售数据库 → 系统**有机会**取得数据
- **Skill**：知道该查哪些表、用什么口径 → 系统**知道怎么**使用数据

> MCP 通常由工具方提供，拿来配置；Skill 由你来写，把你的经验变成 AI 能执行的操作手册。

### 从 Prompt 到 Loop 的完整演进（促销分析案例）

| 阶段 | 做法 | 人的角色 |
|------|------|---------|
| **Prompt** | "帮我分析上周促销数据" | 手动输入，得到通用回答 |
| **+ Context** | 粘入数据，说明对比维度 | 每周手动粘一遍 |
| **→ Skill** | 沉淀分析维度和格式 | 只给数据，按方法执行 |
| **→ Workflow** | 拉数据→分析→图表→结论→确认→发送 | 按一次按钮 |
| **→ Loop** | 每周一自动触发，异常标红 | 从"做分析"变成"审分析" |

> 每往右一步，亲手操作少一层。但**不是必须走到尽头**——每步都要求方法本身更稳定，否则自动化只放大错误。

### 同一份错误报告的诊断表

| 现象 | 问题多半在 |
|------|----------|
| 没指定时间范围和关注指标 | Prompt / Spec |
| AI 没看到退款数据和口径变化 | Context |
| 数据库连接失败却改用缓存 | 连接能力 / Harness |
| 分析方法只看销售额漏了毛利 | Skill |
| 先生成结论后检查数据 | Workflow |
| 工具失败后继续跑 | Harness 运行约束 |
| 文件生成就宣布完成 | Agent 完成状态判断 |

## 九、日常工具箱速查

### 一、让输入更轻

| 技巧 | 适合场景 | 注意 |
|------|---------|------|
| **截图输入** | 界面报错、布局异常、流程图 | 遮挡敏感信息；截图只说明"看起来怎样"，真实状态还需回原系统 |
| **语音输入** | 快速捕捉想法、移动中 | 人名/术语/数字转写后要复核；减少输入摩擦不等于让模糊意图变清楚 |
| **会议转录** | 提取决定和行动项 | 区分"讨论过""建议过""已决定"；行动项含负责人+交付物+时间 |

### 二、让资料可用

| 技巧 | 适合场景 | 注意 |
|------|---------|------|
| **项目空间/持久上下文** | 保存长期有效的项目背景 | 标记来源/版本/日期，定期清理失效内容 |
| **知识库问答** | 从组织资料中按需定位 | 说明来源是否权威、哪个版本有效、冲突时怎么处理 |
| **深度研究** | 多来源搜集、比较和综合 | 明确研究问题和排除项；抽查关键引用；不应自动成为决策依据 |

### 三、让长任务不断线

| 技巧 | 适合场景 | 注意 |
|------|---------|------|
| **会话交接** | 跨会话/跨人/跨 Agent 延续 | 保存目标、状态、已确认决定、约束、未完成事项 |
| **并行会话** | 独立的多项搜集/探索 | 确认无强依赖；多项并行不会自动扩大人的审查能力 |
| **AFK 离场委派** | 范围清楚的长任务 | 用副本/测试环境/脱敏数据；设停止条件；发布/删除/付费仍要人确认 |

### 四、让重复自动发生

| 技巧 | 适合场景 | 注意 |
|------|---------|------|
| **定时任务** | 日报、周报、巡检 | 定义数据截止时间、失败通知和停用条件 |
| **Hook 事件钩子** | 文件保存后跑测试、代码提交后检查格式 | 一个 Hook 一个职责；避免递归触发和静默失败 |
| **事件驱动工作流** | 新文件/工单出现后启动多步流程 | 设计去重、重试、回退、暂停和人工接管路径 |

### 五、跨过没有接口的地方

| 技巧 | 适合场景 | 注意 |
|------|---------|------|
| **界面操作** | 没有 API 的网页/桌面系统 | 在测试账号和受限权限下运行；点击成功 ≠ 目标完成 |
| **手机远程连接** | 查看长任务状态、处理异常通知 | 限制可见数据和可执行动作；不应成为绕过正式授权的通道 |

## 十、术语表

| 术语 | 通俗解释 |
|------|---------|
| Skill | 一类任务的"怎么做"操作手册，可跨任务复用 |
| Spec | 这一次具体做什么、做到什么程度 |
| MCP | AI 连接外部数据和工具的标准协议 |
| Workflow | 多个步骤的编排顺序和异常处理 |
| Loop | 同一目标反复执行直到满足停止条件 |
| Queue | 多项任务的排序和调度 |
| Harness | 把模型、上下文、工具组织起来的运行环境 |
| AFK | Away from Keyboard，离场委派 |
| HIL | Human-in-the-loop，人在回路 |
| Handoff | 会话交接，让任务可以跨会话/跨人延续 |
| Hook | 事件钩子，在特定事件发生后自动触发动作 |

## 核心金句摘录

1. > 让 Skill 变差的不是遗漏，是噪声。

2. > 步骤容易复制，分寸才值得保存。

3. > 最危险的自动化不是停止运行，而是稳定完成一项已经失去价值的工作。

4. > 自动化不会把不可靠的方法变可靠，它只会放大：可靠方法带来规模化收益，不可靠方法带来规模化错误。

5. > 执行越顺畅，错误目标也越容易被高效实现。

6. > 人可以退出重复操作，却不能同时退出学习回路。

7. > 真正的浪费，不是让旧方法退出，而是为了证明过去投入有价值，继续为不再必要的系统支付维护成本。

8. > 人的价值不在于还有多少工作必须亲手完成，而在于能否提出值得解决的问题、识别关键信息、处理例外，并为最终选择负责。
