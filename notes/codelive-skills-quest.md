## 一、核心主题一句话

> **Skill 不是新概念，而是把"最佳实践 + 领域知识"封装起来，让大模型能复用；Quest 1.0 则是让 AI 不止写代码，而是完成整个任务闭环。**

---

## 二、Skill 到底是什么

### 为什么要用 Skill？

大模型是"通才"，但专业领域里的**最佳实践**和**领域知识**往往是缺失的。Skill 就是把这些东西封装成可复用的模块。

```
没有 Skill 时：
  用户：帮我写个测试用例
  AI：拿到代码就开始写，质量不稳定

有 Skill 时：
  用户：帮我写个测试用例
  AI：先读取 Skill 里的测试用例库 → 按照规范构造数据 → 再写用例
```

### Skill 能解决什么问题

| 问题 | Skill 的作用 |
|------|-------------|
| 最佳实践丢失 | 把专家经验固化成标准流程 |
| 领域知识不足 | 把专业资料、词库、模板放进去 |
| 重复枯燥工作 | 自动化执行，释放时间 |
| 输出不稳定 | 用模板和清单约束输出 |

### Skill 的核心优势

1. **渐进式加载**：需要时才读取，节省 token
2. **低成本创建**：主要就是一个 markdown 文件夹
3. **可分享复用**：一次创建，多次使用，团队共享
4. **非程序员也能做**：只要能把需求说清楚，AI 就能帮你生成

## 三、Skill 的核心结构

一个 Skill 本质上就是一个文件夹，里面包含：

```
my-skill/
├── skill.md          # 核心文件：名称、描述、使用时机、执行流程
├── index.md          # 索引文件：告诉模型什么时候读哪个文件
├── docs/             # 参考资料、知识库
├── scripts/          # 可执行的脚本
├── templates/        # 模板文件
└── examples/         # 示例
```

### `skill.md` 的头部信息

```markdown
# 技能名称

## 描述
什么时候使用这个 Skill，它的核心功能是什么

## 使用时机
- 当用户需要做 X 时
- 当用户问 Y 类问题时
```

### 正文内容

- **执行流程**：完成任务的步骤
- **参考资料**：文档、词库、数据
- **示例**：输入输出的样例
- **可执行脚本**：自动化操作

### 渐进式加载

```
传统方式：
  1000 行规则一次性加载 → 很贵很慢

Skill 方式：
  只加载 name + description（几十字）
  需要时再通过 index 找到对应文件读取
  → 高效省 token
```

## 四、Skill vs MCP vs Command vs Role

| 概念 | 一句话理解 | 适合场景 |
|------|-----------|---------|
| **Skill** | 封装最佳实践、流程、知识 | 有标准流程的专业任务 |
| **MCP** | 外部工具/服务接口 | 发短信、抓网页、查数据库 |
| **Command** | 斜杠快捷指令，预设提示词 | 常用操作的一键触发 |
| **Role** | 规范/约束，规定能做什么、不能做什么 | 编码风格、输出格式 |

### 它们的关系

```
你不是在"选技术"，而是在"选怎么 delegating 任务"

老板（你）→ 下属（AI）
  ├─ 需要工具？→ 用 MCP
  ├─ 需要流程？→ 用 Skill
  ├─ 需要规范？→ 用 Role
  └─ 需要快捷指令？→ 用 Command
```

### Skill 和 MCP 的关键区别

| 维度 | Skill | MCP |
|------|-------|-----|
  本质 | 经验/流程/知识 | 外部工具接口 |
| 形式 | markdown 文件夹 | 需要写代码 + 部署服务 |
| 成本 | 低 | 高 |
| 加载方式 | 渐进式 | 调用时加载 |
| 例子 | 字幕校对规范 | 发送短信、爬取网页 |

> 💡 **原则**：它们不是互斥的，而是互补的。一个 Command 可能调用两个 Skill，一个 Skill 也可能调用 MCP。

## 五、Skill 的实战案例

### 案例 1：Code 官方文档搜索 Skill

**场景**：经常要查 Code 官方文档，每次去官网搜索很浪费时间。

**做法**：
1. 用 MCP 抓取 Code 官方文档
2. 把文档整理成 Skill
3. 需要时直接问 AI，自动从 Skill 里找答案

**效果**：
```
用户：我的代码会被提交吗？
AI：读取 skill → 找到 credit.md → 直接回答
```

### 案例 2：学生综合评价 Skill

**场景**：期中/期末考试后，老师需要给学生写评价、生成报表。

**输入数据**：
- 学生基本信息
- 出勤率
- 各科成绩
- 作业完成情况
- 课堂观察记录
- 家长反馈

**输出效果**：
- 班级整体情况
- 每个学生的雷达图
- 个性化评语
- 下学期建议

**为什么用 Skill**：
- 保证每次输出格式一致
- 评语基于真实数据，不是凭空生成
- 可以分享给其他老师复用

### 案例 3：字幕校对 Skill

**场景**：科普直播后，要把视频转文字并校对专业术语。

**传统方式**：人工校对，半小时到一小时，枯燥易错。

**Skill 方式**：
1. 把专业词汇整理成词库
2. 把校对流程写成 Skill
3. 交给 AI 自动处理

## 六、创建 Skill 的最佳实践

### 1. 创建时用最好的模型，使用时可以用稍弱的模型

```
创建阶段：用 GPT-4/Claude 等高级模型
           → 一次性把 Skill 写好

使用阶段：可以用便宜一点的模型
           → 因为流程已经固化，不需要那么强的创造力
```

### 2. 保持简洁，避免不必要的信息

- 上下文越多，模型表现越差，token 越贵
- 不要把大模型已经知道的东西写进去
- 只放**模型不知道但你应该知道**的信息

### 3. 复杂流程要用跟踪清单

```markdown
## 执行步骤
- [ ] 步骤一：分析输入
- [ ] 步骤二：匹配场景
- [ ] 步骤三：选择框架
- [ ] 步骤四：生成输出
- [ ] 步骤五：检查缺失
```

> 💡 清单能避免模型跳过步骤，特别适合流程复杂的 Skill。

### 4. 建立索引，支持渐进式加载

```markdown
## 索引
- 场景 A → 读取 docs/a.md
- 场景 B → 读取 docs/b.md
- 通用规则 → 读取 rules.md
```

### 5. 避免过深的嵌套

- 不要让 Skill 引用另一个 Skill，再引用第三个 Skill
- 层级越多，越容易出问题
- 尽量扁平化

### 6. 用模板保证输出一致性

- 学生评价、报表、文档都有固定格式
- 把模板放在 Skill 里，AI 每次按模板填充

### 7. 用 GitHub 管理 Skill 版本

```
不要把 Skill 只放在 AI 工具里
建议：
  1. 建一个 GitHub 仓库
  2. 把 Skill 文件夹放进去
  3. 每次修改后提交 commit
  4. 写同步脚本自动同步到 AI 工具
```

## 七、常见坑与解决方案

### 坑 1：AI 生成的 Skill 效果不好

**原因**：
- 模型不够强
- 自己没想清楚需求

**解决**：
- 创建 Skill 时坚持用高级模型
- 先人工把流程想清楚，再让 AI 封装

### 坑 2：Skill 没有被调用

**原因**：
- 描述不够清晰，模型不知道何时用
- 同步错了目录
- 路径问题

**解决**：
- 在 `skill.md` 顶部写清楚"何时使用"
- 安装后测试一下是否能被正常识别
- 检查文件路径和目录结构

### 坑 3：上下文还是太长

**原因**：
- 一个 markdown 文件里塞了太多内容
- 没有合理拆分

**解决**：
- 把大文件拆成多个小文件
- 建立索引，按需读取
- 不同场景用不同文件

### 坑 4：Skill 和知识库重复

**判断标准**：

| 场景 | 用 Skill | 用知识库 |
|------|---------|---------|
| 需要标准流程 + 模板 | ✅ | ❌ |
| 只需要检索某句话 | ❌ | ✅ |
| 希望模型始终掌握的知识 | ✅ | ❌ |
| 文档很长，只需匹配片段 | ❌ | ✅ |

> 💡 **原则**：不是替代关系，是互补关系。

### 坑 5：安装太多 Skill 导致冲突

**表现**：
- 模型不知道该用哪个
- 自动决策不符合预期

**解决**：
- 不要装太多 Skill
- 定期清理不用的
- 给 Skill 起清晰、不重复的名字

## 八、Quest 1.0 的设计哲学

### 从"写代码"到"完成任务"

```
传统编程：
  你写代码 → 编译 → 部署 → 测试 → 改 bug

Quest 1.0：
  你说需求 → AI 自己规划 → 执行 → 验证 → 迭代
```

### Quest 1.0 与 Edit 模式的区别

| 模式 | 角色定位 | 适合场景 |
|------|---------|---------|
| **Edit 模式** | 导师/协作者 | 修改现有工程、需要精细控制 |
| **Quest 模式** | 架构师/委托人 | 从零开始、探索性任务、完整闭环 |

### 设计美学：面向非技术人员

- 弱化文件导航
- 弱化代码细节
- 强调"任务是否完成"
- 让用户用自然语言交互

## 九、Quest 1.0 的执行流程

```
        用户需求
           │
           ▼
    ┌─────────────┐
    │   Gazer     │  收集上下文、澄清需求
    │  （感知）    │
    └──────┬──────┘
           │
           ▼
    ┌─────────────┐
    │    Act      │  执行，不限于 coding
    │  （行动）    │  可能包括：写代码、部署、测试
    └──────┬──────┘
           │
           ▼
    ┌─────────────┐
    │   Verify    │  验收结果
    │  （验证）    │  成功 → 结束
    └──────┬──────┘  失败 → 回到 Gazer 重新迭代
           │
           ▼
       任务完成
```

### Interview 机制

当需求不够清晰时，Quest 会自动提问，帮用户明确需求：

```
用户：帮我做个电商网站
AI：你需要用户登录吗？需要支付功能吗？需要后台管理吗？
```

> 💡 这避免了"许愿式提需求"导致的 credit 浪费。

## 十、Token 效率法则

### 核心公式

```
经济模型：
  10 步迭代 × 每步成本 X = 10X

极致模型：
  3 步迭代 × 每步成本 Y = 3Y

如果 3Y < 10X，那么用极致模型反而更便宜、更快
```

### Quest 1.0 的 Auto 模式

- 不需要手动选模型
- 系统根据任务类型自动路由到合适的模型
- 复杂任务用强模型，简单任务用经济模型

### 对开发者的启示

> **不要只盯着单次成本，要看总成本。**

一个强模型可能单次贵，但因为迭代少、错误少，最终可能更省钱。

## 十一、用 Skill 重构 DevOps 流程

### 案例：AI 网关压测

**传统流程**：
1. AI 写压测代码
2. 手动构建镜像
3. 手动推送到仓库
4. 手动部署到 K8S
5. 手动执行压测
6. 手动分析结果
7. 发现问题再改代码...

**Quest + Skill 的流程**：
1. 用自然语言说"帮我做压测"
2. AI 自动：写代码 → 构建镜像 → 推送 → 部署 → 执行压测
3. 自动监控日志和结果
4. 发现问题自我纠偏，重新执行

### Skill 在这里的作用

- **构建 Skill**：知道怎么构建镜像
- **推送 Skill**：知道推送到哪个仓库
- **部署 Skill**：知道 K8S 的 namespace 和 deployment
- **压测 Skill**：知道怎么执行压测、分析结果

### 结果

> "我们不再只是写代码的工人，而是设计流水线的人。"

## 十二、认知债：AI 时代的新风险

### 什么是认知债？

以前有**技术债**：为了赶进度用了临时方案，后面要还。

现在可能出现**认知债**：过度依赖 AI，失去了对代码和系统的理解。

```
不手写 SQL → 不理解索引优化
不手写并发代码 → 不理解锁机制
不自己 debug → 不理解系统运行机制
```

### 风险

- 平时没问题
- 一旦遇到线上故障或拐点问题，会很被动
- 关掉 AI 就不会写代码了

### 建议

| 场景 | 怎么做 |
|------|--------|
| 生产代码 | 保持对代码的感知力 |
| 临时工具/原型 | 可以大胆用 AI |
| 学习阶段 | 不要跳过基础原理 |

> 💡 **原则**：把执行权交给 AI，但把选择权保留在人类手中。

## 十三、给开发者的行动建议

1. **从自己的重复工作入手**——哪些事你每周都在做？把它做成 Skill
2. **先想清楚流程，再让 AI 封装**——Skill 的质量取决于你的流程是否清晰
3. **创建时用高级模型，使用时可降级**——省钱又高效
4. **用清单约束复杂流程**——避免模型漏步骤
5. **建立索引，渐进式加载**——省 token，提速度
6. **用 GitHub 管理 Skill 版本**——方便回滚和同步
7. **不要装太多 Skill**——避免冲突和混乱
8. **Quest 适合完整闭环任务**——Edit 适合精细控制
9. **保持对技术的敏感度**——避免认知债
10. **多实践、多优化**——Skill 和提示词一样，需要迭代
