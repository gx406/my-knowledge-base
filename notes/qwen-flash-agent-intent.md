# 千问闪购 Agent 意图识别与多轮对话架构 · 学习笔记

## 分享背景

关于**千问 APP** 中闪购 Agent 的技术架构讨论，核心涉及意图识别、多轮对话、Planner 编排、上下文压缩等实战问题。

---

## 一、意图中枢

### 核心机制

- **意图中枢**基于一个大型模型，负责意图分类任务
- 不一定路由到子 Agent，简单案例可直接通过 MCP 解决
- **基于多轮对话**：将所有上下文信息文本化，输入给意图模型
- 准确率主要通过 **SFT 微调**提升

### 意图识别方式

- **不使用关键词匹配**，因为可能导致分发错误
- 例如：用户想购买盒马产品时，产品目录包含生鲜和包装食品，关键词搜索会导致困惑
- 采用 **LM 模型**进行意图识别

### 意图体系规模

- 约 **29 种不同意图**
- 意图分类体系在 11-12 月完成 95% 以上，后续仅微调
- 微调方向：将大意图拆解为更小的子分类
- 模型训练与 MCP 开发**可并行进行**

### 意图处理流程

```
用户输入 Q → 意图识别（多轮上下文） → 意图分发 → 路由到对应链路
```

- 所有输入的 Q 都**首先进行意图识别**
- 先识别意图，再根据意图修改 Query（而非传统的先改 Query 再识别）
- 并非所有 Query 都需要搜索

### 多意图处理

- 用户输入可能包含多个意图，系统进行全面分析
- 识别出关键意图后，将复杂意图拆解为 Planner 链路中的任务
- **意图按优先级排列**，而非简单的先来后到
- 最多设置 **5 个意图**，线上通常 1-2 个
- 命中某个意图后**不会中断**，所有意图都会被执行

### 优先级处理示例

> 用户说"购买蜜雪冰城奶茶送到公司"：
> 1. 先处理收货地址（高优先级）
> 2. 再处理品牌和品类搜索

## 二、Fast 模式与 Auto 模式

### 模式选择

- **Fast 模式**在千问版本中被归为 Auto 模式
- 主要在需要与其他渠道对接时使用，直接使用主搜索结果
- 目前**不太常用**，仍在灰度中

### 执行原则

- 每个 Query 只执行**一种模式**
- 由意图中枢拆解，选择相对直接简单的路径：
  - 搜索请求 → 搜索模式
  - 复杂操作 → Planner 的 Mask 模式

---

## 三、Planner 与 Workflow

### Planner 模式

- 当前线上 Planner 模式占比**不高**
- 线上绝大部分 Q 是搜索
- 搜索中进一步拆解使用 Planner，占比可能会很高
- 未来涉及搜索节点编排会增加，且涉及多意图

### 意图依赖处理

- 某些意图存在依赖关系，由 Planner 完成链路规划
- 例如："修改地址 + 蜜雪冰城搜索" → Planner 确定先改地址再搜索
- 当用户修改收货地址后，Agent Memory 中的信息同步更新

### 意图间的依赖

- 例如：查询奶茶后用户想更换选项 → 新意图依赖之前的搜索结果
- 需要从之前结果集中移除已推荐选项，重新推荐

---

## 四、上下文管理与压缩

### 压缩策略

- **每轮对话结束时**进行一次上下文压缩
- 压缩过程**异步进行**，使用较大模型完成
- 关键信息经过 SFT 处理，精选保留内容

### 多轮对话特点

- **无固定轮数限制**，曾处理过几百轮甚至几千轮的对话
- 历史上下文对话会包含在意图模型的 prompt 中
- 商品卡片、商店、商品及价格等信息以文本形式插入

### Memory 压缩细节

- 闪购返回给千问端的数据结构包含商品图片和跳转链接
- 这些在当前处理轮次完成后**对后续 Memory 不需要**
- 压缩前选择丢弃这些信息，节省存储成本和 Token

### AI Native 优化

- 审视 input/output 是否足够 **AI Native 友好**
- 例如：意图分发模型输出通常是 index（1-2 个数字），而非 20 个 JSON token
- 这对线上效率和处理时长影响巨大

---

## 五、MCP 协议与 A2A 架构

### MCP 接口

- 千问与闪购之间通过 **MCP 协议**交互
- MCP 预先定义输入和输出参数：
  - 输入参数：工具具备的参数
  - 输出参数：定义各种边界条件（搜索无结果/有结果/结果不相关时的返回方式）

### A2A 模式

- 采用 **A2A（Agent to Agent）** 模式
- 闪购功能全部交由闪购模块处理，而非 API 式交互
- 千问模块的历史数据会下发给闪购

### 卡片展示

- 确定 JSON 数据结构 → 处理完毕后流式返回给千问
- 千问端根据服务端返回结果进行展示
- 最初采用 Native 卡，目前在做动态化改造
- 视觉规范由千问 UED 团队提供

## 六、模型训练与数据

### SFT 微调

- 训练数据量级：**几十万条**（约 40 万+）
- 数据流程：大模型初筛 → 人工二筛 → 多轮筛选
- **全仓微调**，比原始模型性能提升很大
- 使用 4B 模型训练，整体效率很高

### 训练数据构建

- Planner 中构建 Q 时，需列举各种可能的 MCP 及其返回结果
- **随机模拟**每种情况下的结果，告知 Planner 后续动作
- MCP 的结果是随机的（构建数据阶段）

### RL 展望

- 线上版本还未过渡到 RL 步骤
- 理论上 RL 会有，但需等端到端的 reward 训练成熟
- **当前 SFT 仍有很大发展空间**，不应过分神化 RL

### 槽位提取

- 意图识别过程中槽位提取**不常见**
- 主要发生在搜索模块（如 Query 改写）和 Planner 模块
- 通常在构建训练数据时进行，常见做法是**蒸馏**

---

## 七、评测与质量保障

### 评测方式

| 环节 | 方法 |
|---|---|
| 端到端评测 | 体验 case，产品运营团队每天人工巡检 |
| 算法评测 | 机器自动化评测，在模型训练和微调阶段执行 |
| 标准评测 | 便于模型迭代对比 |

### 流式返回

- 为保证用户体验，**必须支持流式处理**
- 当前多意图在 Planner 中是**串行执行**
- 当前意图处理完毕后，通过 MCP 接口将结果流式返回

---

## 八、异常处理与边界情况

### 执行失败

- 如遇到失败，程序会**退出循环**，不会卡死
- 有相应的异常处理机制

### 节点依赖

- 一个节点可能依赖前置节点的关键输出
- 例如：支付环节需要订单信息
- 在 Memory 中实时判断订单状态，待支付则继续处理支付流程

### 对话上下文中业务参数

- 对话上下文中业务参数的获取和锚定是关键环节
- 合法性校验与传统 APP 方法截然不同
- 对上下文的深入理解至关重要

---

## 九、未来演进方向

### 意图数量增长问题

- 随着意图数量增加，意图识别的 prompt 也会增多
- **正在改造**：采用一个大 Planner 解决意图并分配到合适的工具

### 地址与搜索的优先级迭代

- "下单至蜜雪冰城至公司"被拆解为独立的"地址搜索"意图
- 这体现了意图分类树的**持续迭代**

## 核心概念对照

| 概念 | 说明 |
|---|---|
| 意图中枢 | 基于大模型的意图分类系统，多轮对话输入 |
| Fast/Auto 模式 | 快速通道，直接使用搜索结果，目前少用 |
| Planner | 复杂任务的编排器，处理多意图和依赖关系 |
| MCP | 千问与闪购之间的协议接口 |
| A2A | Agent to Agent，闪购功能交由闪购模块处理 |
| Memory 压缩 | 每轮对话后异步压缩上下文，丢弃不必要的信息 |
| SFT | Supervised Fine-Tuning，主要训练手段 |
| Query 改写 | 搜索关键词的改写，与意图识别是不同任务 |

---

## 个人总结

千问闪购 Agent 的核心设计哲学：**小模型 + 大数据 + 精细化工程**。

三个最有价值的洞察：
1. **意图识别先于 Query 改写**——先理解"用户想干什么"，再处理"怎么搜"
2. **SFT 仍有巨大空间**——不急于上 RL，先把 SFT 做扎实
3. **AI Native 的输出设计**——意图模型输出 index 而非 JSON，极致优化推理效率
